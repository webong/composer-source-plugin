# Publish workspace packages and discover them through Packagist

The initial publisher generalizes Gateway's split-and-index workflow. It is author tooling: consumers install normal Composer packages with independent dependency graphs. No custom `require` constraint or runtime module downloader is introduced.

## Author: one repository, many package roots

Every module owns a normal `composer.json` with a unique package name, autoload metadata and dependencies. Reuse the existing workspace list:

```json
{
  "name": "acme/toolkit-catalog",
  "type": "metapackage",
  "extra": {
    "source-plugin": {
      "workspaces": ["php/*", "adapters/*"],
      "catalog": {
        "url": "https://raw.githubusercontent.com/acme/toolkit/dist/composer/composer-packages.json",
        "packages": ["acme/core", "acme/laravel"]
      }
    }
  }
}
```

Install and allow Composer Source Plugin before using its commands. These commands are available in plugin 0.5.0 and newer. The root metapackage can be published on Packagist using the normal root-manifest/tag workflow. Packagist indexes that catalog package; it does **not** index the nested packages. The catalog needs no runtime requirements merely to advertise the index, and can have the plugin in `require-dev` for author development.

```sh
composer source:publish list
composer source:publish release --release-version=1.0.0 --dry-run
composer source:publish release --release-version=1.0.0
composer source:publish verify --composer
# Only after reviewing generated refs:
composer source:publish release --release-version=1.0.0 --push
```

Commands read committed manifests at `HEAD` (or `--ref`), not uncommitted workspace edits. `git subtree` must be installed. Each selected directory is split into its own Git history, still inside the **same repository**:

```text
dist/acme/core              package-root source history
acme/core/v1.0.0            immutable package release tag
dist/acme/laravel           another package-root history
acme/laravel/v1.0.0         another package release tag
dist/composer              generated README.md and composer-packages.json
```

Full vendor/package identities avoid cross-vendor name collisions. These generated refs differ from Gateway's short-name refs; this tool does not read or migrate Gateway publication. Root `workspaces` is the discovery contract; no fixed `pkg`/`mod` layout is assumed. `type: project` workspaces are skipped. Initially only libraries and metapackages are published. Overlapping roots, symlinks/submodules within packages, escaping autoload/bin paths, checked-out publication refs and metadata branches containing unrelated files are refused.

`release` splits all selected packages, maps internal `dev-main`/`@dev` requirements to `^X.Y.Z` in the **index metadata**, creates package tags and generates a deterministic version index. Existing tagged bytes are never rewritten; attempting to reuse a version at another split commit fails. `dev-main` records track generated package branches and preserve dev requirements. This initial version uses one shared release version; independent package release schedules are not implemented.

Metadata is read from each version's own manifest. Source and GitHub ZIP URLs reference its exact **split commit**, whose tree has the package manifest at its root. Thus plain Git source installations and ZIP installations share normal autoload/resource/bin roots; there is no custom archive extraction. The split reference is not the original monorepo commit. Root-only development settings are removed from index records. GitHub archives use Git commit-addressed URLs with no archive checksum generated by this tool; it does not claim signed artifact inventories, SHA-256 verification or a secure supply-chain attestation feature.

Nothing is pushed without `--push`. That flag requests an atomic remote push of branches, tags and metadata. Local refs are updated sequentially after validation; a disk/Git failure may need an inspected rerun. A dry run leaves refs unchanged but may create Git objects and writes `composer-packages.json` if `--out-dir` is explicitly supplied. The author controls generated index contents and release retention.

`--release-version` avoids Composer's reserved global `--version` flag. The checkout-only `php bin/source-publish` helper instead accepts `--version`.

Other actions: `split` updates only package branches; `metadata` regenerates the index from existing branches/tags; `verify` checks sibling constraints. `verify --composer` also checks that Composer lists versions; the integration suite separately tests actual installation. Options include `--repo`, `--ref`, `--remote`, `--source-url`, `--dist-url` with `{sha}`, `--metadata-branch`, `--out-dir`, and an explicit `--force-branches` escape hatch for rewritten generated branch history. That escape hatch never replaces existing package tags.

## Consumer: discover once, then normal require

Install and allow a version of this plugin containing these commands first. The plugin cannot register a command in the solve that first installs it. Then:

```sh
composer source:catalog acme/toolkit-catalog:^1 --dry-run
composer source:catalog acme/toolkit-catalog:^1
composer require acme/laravel:^1
```

The command resolves the catalog using Composer's configured repositories (Packagist by default), reads `extra.source-plugin.catalog` from its package metadata and writes **one** named standard Composer repository to the root manifest. It does not download or execute the catalog package, install its dependencies, change `require`, or add consumer `extra` settings. The catalog is a discovery record, not a mandatory installed carrier. Exact package-name filters restrict the repository's authority; wildcard filters are rejected. HTTPS without embedded credentials is required. `--allow-local` permits local file indexes for tests only. Repeated registration of identical settings is a no-op; a changed endpoint/filter set requires explicit review and removal of the old registration.

The resulting manifest has ordinary requirements:

```json
{
  "require": {"acme/laravel": "^1"},
  "repositories": {
    "source-acme--toolkit-catalog": {
      "type": "composer",
      "url": "https://raw.githubusercontent.com/acme/toolkit/dist/composer/composer-packages.json",
      "canonical": true,
      "only": ["acme/core", "acme/laravel"]
    }
  }
}
```

Composer versions may serialize named repository entries as a list instead; both formats work. The index resolves sibling dependencies before installation. `composer.lock` records exact package versions and source/dist commits. After registration, fresh installs and updates use the standard repository and do not require catalog lookup or plugin code. Locked `install --no-dev --no-plugins`, source reinstall and ordinary partial updates retain stock Composer behavior. Other plugin features such as projections still require their own normal setup.

## Packagist and operational limits

This works **with a Packagist-discovered catalog**, not by modifying Packagist's server-side module discovery. Consumers who prefer can add the advertised URL directly and use no plugin at all. A single plain `composer require acme/laravel` on a fresh project with only public Packagist remains unsupported unless that package is itself published there through a supported arrangement.

Publish the index **before** advertising its URL in a catalog release. Keep every indexed split commit reachable through retained branches/tags. Never replace stable tags. Canonical repositories hide lower-priority sources for listed package names: include and verify any historical versions that consumers must retain. The first version discovers the current workspace set; removing a package from that set removes its records from a regenerated index, so package retirement/history retention needs deliberate author review. Registering a catalog does not migrate old public releases or old lock URLs.

Registration records the endpoint/filter set, not the catalog version as an installed dependency. It is a one-time configuration operation, not a promise that the catalog or mutable index is itself locked. Package commits are locked by Composer normally. The command does not validate index reachability; the next Composer solve does. Host outages, credentials, Composer cache/offline behavior and raw-host propagation delays remain standard operational concerns. Use Composer authentication configuration; never publish tokens in metadata. Private-host redirect/auth behavior and public Packagist publication have not been exercised by the local fixture.

Current validation uses temporary repositories and a Composer-protocol catalog fixture with Packagist disabled. It tests deterministic splitting, stable/dev dependency resolution, release refusal, atomic local-remote pushes, module-root installation, catalog registration and locked plugin-disabled installation. No live package/release/registry changes are made. The separate design document describes broader future hardening; it is not a statement that every proposal there is implemented.

## Keep the index on the normal branch

A dedicated metadata branch is optional. To generate the index into the normal checkout instead:

```sh
composer source:publish release --release-version=1.0.0 --no-metadata-branch --out-dir=composer
# Review and commit composer/composer-packages.json on your normal branch.
```

For an existing set of split branches/tags, use `source:publish metadata` with the same two flags. This mode never creates or updates `dist/composer`, and it does not commit or push the normal branch for you. `--no-metadata-branch` requires `--out-dir` and conflicts with `--metadata-branch`. On the `release` action, an explicit `--push` pushes only generated package branches/tags; commit and push the index on the normal branch separately, after those refs are reachable. The `metadata` action rejects `--push` in file-only mode to avoid implying that output files were published.

Advertise the full URL of the committed file in the catalog, for example:

```json
{"url": "https://raw.githubusercontent.com/acme/toolkit/main/composer/composer-packages.json", "packages": ["acme/core", "acme/laravel"]}
```

The file is `main:composer/composer-packages.json`. Use `--out-dir=.` and a raw URL ending in `main/composer-packages.json` instead if you want `composer-packages.json` at the repository root. Package-root split branches are still needed for the current source/dist installation strategy; this option removes only the dedicated **metadata** branch. Use a generated output directory outside selected workspace roots so the index does not enter a package's own split history.

Composer accepts an explicit JSON index URL, so `composer-packages.json` needs no `packages.json` alias or wrapper. Directory-only repository URLs still make Composer look for its conventional `packages.json`; use the full filename for indexes generated by this publisher.
